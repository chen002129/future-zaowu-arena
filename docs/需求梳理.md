## 一、产品定位

**一句话定位：** 面向国内开发者的 AI 赛事 / 黑客松信息聚合小程序——把散落在各处的比赛信息收进一个列表，让用户三步内判断"这场我该不该报"。

**与 HackerTrip 的差异：**

| 维度   | HackerTrip            | 本产品                     |
| ---- | --------------------- | ----------------------- |
| 侧重   | 黑客松发现 + 技术栈匹配 + 参赛工作流 | **AI 赛事时讯聚合 + 信息提醒**    |
| 内容板块 | 赛事为主                  | 赛事 + AI 行业资讯 + 经验攻略     |
| 信息更新 | 人工 + 半自动              | **自动抓取 + 人工审核**（后台可运营）  |
| 参赛辅助 | 身份卡、Skills 同步、个人赛程    | 收藏 + 截止提醒（一期聚焦，身份卡后续再议） |

**目标用户：** 国内高校学生 + 独立开发者，想参加 AI 赛事但信息获取成本高、容易错过截止时间。

**核心价值：** 降低"错过率"——赛事信息寿命极短，一个持续更新的聚合列表 + 截止提醒，价值远高于泛泛的社区讨论。

---

## 二、核心用户场景

1. **找赛**：用户打开小程序 → 按「AI Agent / 大模型 / 线上 / 本月截止」筛选 → 找到符合方向的赛事。
2. **判断**：进入详情页 → 看时间、奖金、资格、报名要求 → 一键跳转官网报名。
3. **不错过**：收藏感兴趣但还没准备好的赛事 → 授权订阅提醒 → 截止前收到微信推送。
4. **顺便长知识**：刷「资讯 / 攻略」板块，了解 AI 行业动态和参赛经验。

## 五、数据来源与抓取策略

### 5.1 抓取源清单

> 已基于 HackerTrip 公开站点反向拆解出真实来源构成，完整版见 **`docs/抓取源清单.md`**。

**先纠正一个认知：HackerTrip 不是纯爬虫，而是「少数源自动抓 + 大量人工录入」。** 它自己在数据方法页写明「**自动采集结果不会天然等于事实**」，且设有「主办方提交赛事」入口。它的 34 场在售赛事中，近 1/3 来源（公众号 3 + 飞书表单 4 + 腾讯文档 1）是**抓不到、只能人工**的。

| 类型            | 真实示例                        | 条数占比    | 抓取难度     | 处理方式                       |
| ------------- | --------------------------- | ------- | -------- | -------------------------- |
| 活动平台          | **lu.ma**、活动行、Meetup        | 高（4/34） | **低**    | 有公开 JSON/RSS，**一期首选**      |
| 数据竞赛平台        | 阿里天池、Kaggle、DataFountain、和鲸 | 中       | **低**    | 列表页规范，解析器成本低               |
| 国际赛事聚合        | lablab.ai、ETHGlobal         | 中       | 低        | 结构规范，扩充 AI / Web3 内容       |
| 大厂赛事页         | 腾讯云、NVIDIA、天猫、支付宝、抖音        | 中       | 中        | 各自独立模板，逐个写解析器              |
| 零散官网          | 各主办方独立域名                    | 低但数量多   | **高**    | 一站一模板，**性价比最低，交给人工或主办方提交** |
| **报名表单**      | 飞书表单、腾讯文档                   | 高（4+1）  | **不可枚举** | 无公开目录，只能拿到链接后录入            |
| **公众号 / 小红书** | 主办方推文、小红书笔记                 | 高（3+）   | **不可抓**  | 后台一键粘贴链接 → 半自动解析 / 人工录入    |

**结论：** 一期不铺源，优先做三件事——① 接 lu.ma 与天池；② 把「粘贴链接 → 半自动解析成结构化赛事」做顺；③ 开放主办方自助提交入口。**真正难拿的信息（公众号、飞书表单）恰恰是别处搜不到、用户最需要的那部分，这里才是建立壁垒的地方。** |

### 5.2 抓取流程

```
定时触发（云函数定时器）
  → 拉取各源列表页
  → 站点对应解析器抽取字段
  → 归一化（时间格式、城市、主题标签）
  → 下载赛事海报 → 转存云存储（拿 fileID）
  → 去重（按 官网 URL + 标题相似度）
  → 落库为「待审核」状态
  → 后台人工审核 → 发布
  → 生成快讯（新收录）→ 刷新首页实时条

【时效复核 · 每 2 小时，独立于抓取】
refreshStatus
  → 重算全部赛事状态（报名中 / 即将截止 / 已截止 / 进行中 / 已结束）
  → 比对截止时间、奖金等关键字段 → 有变动则写 deadlineHistory 并标 deadlineChanged
  → 生成快讯（截止变更 / 临近截止）→ 推送订阅提醒
```

### 5.3 关键约束

- **反爬**：需控制频率、加随机间隔；部分站点可能需要人工兜底。
- **公众号**：微信不开放抓取，走「半自动」——管理员粘贴文章链接，系统尝试解析正文关键词，或直接人工录入。
- **海报**：抓取时**必抓**（优先级 `og:image` > 页面首张大图 > banner），**存自己的对象存储、绝不热链**；命名 `{slug}-{原图URL短哈希}.{ext}`，短哈希用于去重。抓不到海报时用固定模板生成兜底，绝不用灰色占位图（详见《视觉设计规范》第十一节）。
- **报名二维码**：海报里常带二维码，**单独裁出一份存起来**，详情页提供「长按识别 / 保存到相册」——小程序场景下比跳外链顺。此做法取自 HackerTrip。
- **版权**：只做信息索引与摘要，详情引导跳转官方原文，不整篇搬运。**赛事海报版权归原作者所有**，仅作信息展示，接到投诉立即下架。

### 6.1 云函数清单

| 云函数                    | 触发方式                                | 职责                                                        |
| ---------------------- | ----------------------------------- | --------------------------------------------------------- |
| `crawlFetch`           | 定时（**分层频率**：高频源每 2–4 小时 / 官网每日 1 次） | 遍历启用的抓取源，拉取列表                                             |
| `crawlParse`           | 由 crawlFetch 调用                     | 按源类型解析、归一化、去重、入库待审                                        |
| `refreshStatus`        | 定时（每 2 小时）                          | **状态机器**：重算赛事状态（未开始/报名中/即将截止/已截止/进行中/已结束）；检测截止时间变更并写入变更记录 |
| `genFlashes`           | 由 crawlParse / refreshStatus 调用     | 依据「新收录 / 截止变更 / 临近截止」**自动生成快讯**                           |
| `sendReminder`         | 定时（每日 9:00 / 20:00）                 | 扫描临近截止的订阅，调用订阅消息推送                                        |
| `adminApi`             | HTTP 调用                             | 后台登录、审核、增删改查、看板                                           |
| `getCompetitions`      | 小程序云调用                              | 列表 + 搜索筛选                                                 |
| `getCompetitionDetail` | 小程序云调用                              | 详情                                                        |
| `toggleFavorite`       | 小程序云调用                              | 收藏 / 取消                                                   |
| `saveSubscription`     | 小程序云调用                              | 保存订阅提醒授权                                                  |
| `login`                | 小程序云调用                              | 换取 openid、写用户                                             |

| 触发器               | 频率             | 说明                              |
| ----------------- | -------------- | ------------------------------- |
| `crawlFetch`（高频源） | 每 2–4 小时       | 竞赛平台 / 技术社区 / 活动页——更新最频繁的一类     |

## 七、关键技术约束与风险（务必注意）

1. **订阅消息的限制（最大坑）**
   - 小程序订阅消息分「一次性订阅」和「长期订阅」。
   - **一次性订阅**：用户授权一次只能发一条，需要用户主动点击「订阅提醒」按钮。
   - **长期订阅**：仅限部分类目（政务、医疗、教育等）可申请，普通工具类目通常拿不到。
   - **结论**：截止提醒必须设计成——用户在收藏时主动点「提醒我」→ 一次性授权 → 发一条。用户需要多次提醒时，需在授权时批量订阅多条（微信支持一次勾选多个模板/多次）。
   - 这块要在产品交互上做引导，否则提醒功能形同虚设。
2. **抓取合规**：控制频率、遵守 robots、只做摘要索引并跳转原文。
3. **内容审核**：抓取内容必须过人工审核才能发布，避免错误/过时信息误导用户。
4. **小程序类目与资质**：需确认「信息资讯」类目是否需要额外资质（个别类目要求《互联网新闻信息服务许可证》）；**建议定位为「工具/效率」类目，资讯只做赛事相关**，避免触发新闻资质要求。

| 阶段          | 范围                                                  | 目标                |

| **二期**      | 扩充抓取源、加资讯/攻略板块、数据看板完善                               | 内容更全、运营更顺         |
| **三期**      | 技术栈匹配推荐、身份卡、组队广场、日历视图                               | 提升留存与差异化          |

**建议一期先只接 1–2 个最好抓的源（如数据竞赛平台）**，把整条链路跑通，再扩源。抓取是最容易失控的环节，不要一开始铺太宽。

## 十、公众号 + 小程序联动方案

> 2026-10-07 新增。用户希望「部署到公众号」，已澄清形态为 **公众号推文 + 小程序功能联动**。

### 10.1 分层分工

| 层   | 平台      | 职责                                   |
| --- | ------- | ------------------------------------ |
| 触达层 | **公众号** | 推送赛事时讯图文、自定义菜单入口、图文内嵌小程序卡片           |
| 功能层 | **小程序** | 列表 / 搜索筛选、详情 / 跳转报名、收藏、订阅提醒          |
| 数据层 | 微信云开发   | 抓取 → 审核 → 发布 → 推送；公众号与小程序**共用同一套数据** |
| 来源层 | 外部赛事源   | 官网 / 竞赛平台 / 社区                       |

### 10.2 三条联动通路

1. **公众号 → 小程序**：自定义菜单直接跳小程序页面（如「找赛事」→ 列表页）；图文内插入小程序卡片。
2. **小程序 → 公众号**：小程序内放「关注公众号」引导（`official-account` 组件，需已关联）。
3. **云开发 → 公众号**：抓取到的赛事汇总 → 后台排版成图文 → 推送到公众号草稿箱 / 群发。

### 10.3 前置条件（必须满足）

1. 公众号需**完成微信认证**才能关联小程序（个人主体无法认证）。
2. 小程序需完成认证（个人主体小程序可注册，但部分能力受限）。
3. 同一主体最佳；不同主体需双方管理员确认授权。
4. 关联路径：公众号后台 → `广告与服务 → 小程序管理 → 关联小程序` → 输入小程序 AppID → 小程序管理员确认。

### 10.4 订阅号 vs 服务号（对「时讯」的影响）

| 对比项  | 订阅号        | 服务号          |
| ---- | ---------- | ------------ |
| 注册主体 | 个人 / 企业    | **仅企业 / 组织** |
| 群发频率 | 每天 1 次     | 每月 4 次       |
| 消息位置 | 折叠进「订阅号消息」 | 直接进聊天列表      |
| 触达强度 | 弱          | 强            |
| 高级接口 | 认证后部分开放    | 认证后完整（模板消息等） |

**结论：** 想做「每日一推」，订阅号频率更合适，但折叠导致打开率低；服务号触达强但每月只有 4 次。  
**推荐折中**：以「小程序 + 订阅消息」承载**个性化提醒**，公众号只做**每周精选 / 重要赛事**的高质量推送。

### 10.5 对原方案的影响

- 后端不变（仍走微信云开发），只是新增一个「图文生成 + 推送」模块。
- 新增数据表：`mp_articles`（推文草稿）、`mp_push_logs`（推送记录）。


- 新增云函数：`genWeeklyDigest`（聚合本周赛事 → 生成图文）、`pushToMp`（推送草稿箱 / 群发）。
- 管理后台新增「推文」模块：选赛事 → 排版 → 预览 → 推送草稿箱。

### 10.6 公众号自查方法（2 分钟）

登录 [mp.weixin.qq.com](https://mp.weixin.qq.com) → 左侧底部 `设置与开发 → 公众号设置 → 账号详情`，确认三件事：

| 要确认的               | 在哪看           | 影响                |
| ------------------ | ------------- | ----------------- |
| **账号类型**：订阅号 / 服务号 | 账号详情页顶部       | 决定群发频率与高级接口       |
| **认证状态**：已认证 / 未认证 | 账号详情页顶部标识     | **未认证则无法关联小程序**   |
| **主体类型**：个人 / 企业   | `账号详情 → 主体信息` | 个人主体无法认证，也无法注册服务号 |

**快速肉眼识别：** 消息折叠在「订阅号消息」文件夹里 = 订阅号；直接出现在聊天列表 = 服务号。

## 十一、时效性机制（产品的命门）

> 2026-10-07 新增。用户明确要求「讯息一定要紧跟时事」。这不是一句态度，必须落成机制。  
> 核心判断：**信息会老、会变、会过期。** 一个赛事聚合产品最容易死的地方，就是列表里躺着已经截止、甚至被主办方延期了的旧信息——用户被误导一次就再不回来。

### 11.1 三个层次，缺一不可

| 层次        | 要解决的问题             | 机制                                                                                    |
| --------- | ------------------ | ------------------------------------------------------------------------------------- |
| **① 收录快** | 新赛事第一时间进列表         | 抓取**分层频率**：高频源每 2–4 小时、官网每日 1 次；抓到的条目 24 小时内打 `NEW`                                   |
| **② 变更准** | 主办方改了截止/奖金，列表必须跟着改 | `refreshStatus` 每 2 小时复核；检测到变更写 `deadlineHistory`，前端&#x6253;**「截止变更」**&#x89D2;标并高亮新日期 |
| **③ 状态活** | 已截止的不该混在报名列表里      | 状态由系统**自动流转**（报名中→即将截止→已截止→进行中→已结束），不靠人工点「标记结束」                                       |

**一句话：抓取负责「快」，复核负责「准」，状态机负责「活」。** 三者合起来才叫"时讯"。

### 11.2 面向用户的时效表达

- **顶部实时条**：首页常驻一条"活"的快讯（红点脉冲 + 相对时间"16 分钟前"），点进时讯页。
- **相对时间**：所有时间用 `刚刚 / N 分钟前 / N 小时前 / 昨天 / N 天前`，不用绝对日期——相对时间才有"新鲜感"。
- **NEW 角标**：24 小时内新收录 / 更新的赛事，卡片右上角蓝色 `NEW`。
- **截止变更角标**：截止时间被改动过的，右上角红字「截止变更」，卡片日期变红。
- **今日更新计数**：列表标题显示"今日 N 更新"，让用户一眼知道这里**是活的**。
- **核验凭证**：详情页顶部固定一行「核验于 X 小时前 · 来源」，把"我们盯过"这件事显性化——这是信任的来源。
- **变更留痕**：详情页单列「截止时间变更」段落，展示 `原截止 → 现截止` 与同步时间。
- **排序默认「最新更新」**：而不是纯按截止时间。用户先看到"发生了什么新事"，再决定看不看。

### 11.3 快讯（flashes）与资讯（articles）的分工

两者必须分开，否则会互相拖累：

|    | 快讯 flashes                 | 资讯 / 攻略 articles   |
| -- | -------------------------- | ------------------ |
| 长度 | 一句话                        | 长文                 |
| 时效 | **分钟~小时级**，会过期             | 长尾常青，不追求时效         |
| 生成 | 抓取/复核**自动生成**为主            | 人工撰写 / 精选转载为主      |
| 位置 | 时讯页顶部时间线；首页实时条             | 时讯页下方「精选专栏」        |
| 例子 | "天池 AI Agent 赛报名延期至 11.05" | "48 小时黑客松的 7 个节奏点" |

### 11.4 运营红线

1. **宁可少，不可旧。** 抓取失败或长时间未核验的赛事，状态标注「信息待核验」或直接下架，绝不放任它长期"看起来很新"。
2. **截止已过必沉底。** 已结束的赛事默认折叠，不占用列表主视野。
3. **变更必须留痕。** 主办方延期/提前，一律以"变更"形式呈现，不能静默改数字——否则用户会怀疑数据被篡改过。

### 11.5 对 MVP 的影响

- 原型（`design/mvp.html`）已实现：首页实时条、最新/截止双排序、`NEW` 与「截止变更」角标、今日更新计数、时讯页快讯时间线（自动/人工两种来源区分）、详情页核验凭证 + 变更留痕、实时倒计时。
- 后端新增：`refreshStatus`、`genFlashes` 两个云函数，`flashes` 集合，`competitions` 五个时效字段。
- 管理后台新增：快讯管理（自动生成列表 + 人工发布）、变更告警（哪些赛事截止被改动过）。
