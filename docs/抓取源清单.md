# 抓取源清单 · 基于 HackerTrip 反向拆解

> 状态：v1.1 · 2026-10-07（v1.1 新增第六章：HackerTrip 作为兜底聚合源的接入方案）
> 方法：你给的是微信小程序分享链接（`#小程序://HackerTrip/...`），浏览器打不开。但 HackerTrip 有同源公开站点 `hackertrip.space`，我直接抓了它的**公开数据接口、方法说明页、页面图片存储**，反推出了它的数据来源与海报机制。

---

## 一、先说结论：HackerTrip 不是纯爬虫，是「抓 + 人工核对」

这点非常重要，直接决定我们的工程量。三条硬证据：

1. **它自己承认的**。`hackertrip.space/methodology`（数据方法页）原文：

   > 团队按**来源一致性、信息完整度与更新时间**进行核对。**自动采集结果不会天然等于事实**；存在冲突时，主办方最新公告和可验证的书面材料优先。

2. **它有「主办方提交赛事」入口**。官方 CLI 里有一条 `submit-event` 命令，主办方可零门槛把活动提交到平台草稿箱。也就是说**一部分内容根本不是抓来的，是送上门的**。

3. **它的更新字段写得很克制**：明确写「页面更新时间表示 HackerTrip 内容更新，**不代表主办方公告时间**」。这是被坑过才写得出来的话。

**对我们的启示：不要一开始就幻想"全自动抓取"。一期应该做成「少数几个源自动抓 + 公众号/小红书人工录入」的混合模式**，这跟 HackerTrip 的实际做法一致。

## 二、它公开的数据接口（可直接抄结构）

| 能力 | 地址 | 说明 |
|------|------|------|
| **赛事全量 JSON** | `https://hackertrip.space/api/hackathons` | **⭐ 首选**。数组，37 条，33 字段全覆盖，**直接带 `coverImage`**，`auth: none` |
| 赛事 JSON feed（精简） | `https://hackertrip.space/api/match?limit=100` | 仅「即将开始 / 进行中」，无海报字段，`limit` 上限 100 |
| 同上 markdown 格式 | `https://hackertrip.space/api/match?format=markdown` | 适合直接喂 LLM 摘要 |
| 给 LLM 读的站点说明 | `https://hackertrip.space/llms.txt` | **含 Public Event Feed 公开声明 + 引用边界**（见第六章） |
| Agent 能力清单 | `https://hackertrip.space/.well-known/agent.json` | 声明各端点认证要求 |
| 数据方法说明 | `https://hackertrip.space/methodology` | |
| 赛事列表页 | `https://hackertrip.space/explore` | |
| 开源仓库 | `https://github.com/Jayden72Huang/hacker_trip` | |

## 四、海报机制（你说「他的海报都可以放进去」，确实可以）

我把它的图片存储规律扒出来了：

### 存储与命名

```
https://pub-d7a436bb140a401a98a2b96d1850d970.r2.dev/hackathons/covers/{slug}-{描述}-{12位hash}.{jpg|png}
```

实例：

```
雾客松-2027-wakeathon-重庆跨年-ai-黑客松-47603359f78e.jpg
苏客松-2026-su2026-苏州-ai-黑客松-b19a3586502e.jpg
天猫ai黑客松-高校挑战赛-5a7674a103c6.png
```

**结论：**
- 它用 **Cloudflare R2** 自建图床，**不热链主办方图片**——这点很专业，避免了源站改图/防盗链导致封面挂掉。
- 文件名 = **slug + 描述词 + 12 位短哈希**。哈希应是原图 URL 的指纹，用来**去重**（同一张海报不会被存两次）。
- 当前共 **22 张封面**（含二维码图），对应 34 场赛事中的一部分。

### 一个被忽略的细节：它单独存了「报名二维码」

```
苏客松-2026-su2026-苏州-ai-黑客松-qr-01d16d9ceade.jpg
雾客松-2027-wakeathon-重庆跨年-ai-黑客松-qr-bb561f24f216.jpg
```

海报里常带报名二维码，它**把二维码单独裁出来存了一份**。这在小程序场景里价值很高——用户可以长按识别或保存二维码去报名，比跳外链顺。**建议我们直接抄这个做法。**

### 我们的海报采集方案（建议）

| 环节 | 做法 |
|---|---|
| 抓取时机 | 抓赛事时**必抓**，优先级：`og:image` > 页面首张大图 > 主办方 banner |
| 存储 | 存**自己的对象存储**，绝不热链。命名 `{slug}-{原图URL短哈希}.{ext}`，哈希做去重 |
| 规格 | 原图转存，宽 ≥ 750px，JPG/PNG/WebP，单张 ≤ 500KB，保留 **3:4 及以上**比例 |
| 二维码 | 顺带把海报里的二维码区域裁出来存一份，详情页提供「长按识别 / 保存到相册」 |
| 兜底 | 抓不到 → 用生成式海报模板（浅灰 + 工程网格 + 等宽日期 + 品牌水印），**不用灰色占位图** |
| 合规 | 海报与二维码版权归原作者所有，仅作信息展示，接到投诉立即下架；详情页保留「查看主办方原文」 |

> 原型说明：`design/mvp.html` 里 34 场真实赛事的 18 张海报，为演示效果临时引用了 HackerTrip 的公网图片地址（带 `onerror` 兜底，加载失败自动露出模板海报）。**生产环境的正确做法是抓取时从主办方原页下载、转存自己的存储**，不引用第三方图床。

## 五、给我们的源接入优先级（一期）

| 优先级 | 源 | 理由 |
|---|---|---|
| **P0** | lu.ma 活动页 | 条数最多（4/34）、有公开接口、更新最勤——最快跑通闭环 |
| **P0** | 天池 / 腾讯云赛事页 | 国内大厂，结构稳定，中文信息完整，用户关心度高 |
| **P0** | 人工录入通道 | 公众号 3 条 + 飞书 4 条 + 腾讯文档 1 条，占近 1/3，**一期必须有顺手的录入工具** |
| P1 | lablab.ai / ETHGlobal | 扩充 AI 与 Web3 国际赛事 |
| P2 | 主办方自助提交入口 | 长期最省力的来源，等有用户量再做 |
| 不做 | 一站一模板的零散官网 | 性价比最低，交给人工或主办方提交 |

**核心结论一句话：一期不要铺源，要铺「人工录入 + 半自动解析」的能力。** 因为真正难拿的信息（公众号、飞书表单）恰恰是别处搜不到、用户最需要的那部分。

## 六、兜底聚合源：把 HackerTrip 当「发现层」用

> v1.1 新增。对应你说的「**我们抓不到的就去他这里抓**」——成立，但**必须先定一个前提**，否则会踩坑。

### 6.1 前提：抓它的「线索」，不抓它的「结论」

HackerTrip 在 `llms.txt` 里**自己写死了引用边界**（原文）：

> 涉及某一场具体赛事的报名状态、截止时间、奖金、场地、参赛资格或主办方身份时，请**以该赛事主办方的官方页面为准**并**优先引用官方来源**。HackerTrip 是**发现与比较层，不是第三方赛事变更的最终权威**。

这句话对我们极其有利——**它自己承认自己是中间层**。所以我们从它这里抓到的，定义上就是**线索**，不是事实。这条边界正好和我们第十一章的「时效性核验机制」严丝合缝：**从它发现 → 回溯主办方核验 → 才敢发布**。

**结论：把它当 L2「发现层」，不当内容源。** 这不是妥协，这比硬爬一堆官网更符合我们产品的可信度定位。

### 6.2 合规判断（这段必须看，否则会做错）

| 证据 | 内容 | 含义 |
|---|---|---|
| `robots.txt` | `User-Agent: *` → **`Disallow: /api/`** | 挡的是**搜索引擎收录** API 页面 |
| `llms.txt` | 单列 **"Public Event Feed"** 章节，给出 JSON / Markdown 地址与 `limit` 参数 | **主动面向 AI Agent 开放的数据接口** |
| `agent.json` | `/api/hackathons` 标注 **`authentication: none`** | **无需认证的公开端点** |

**判定：该 feed 是它面向 AI 主动开放并文档化的公开接口，不属于绕过反爬。** 但仍须遵守：标明身份、控制频率、不镜像转发、标注来源。

### 6.3 它能补上什么（对照第三章的缺口）

| 第三章识别出的缺口 | 条数 | 接入聚合源后 |
|---|---|---|
| 公众号推文（不可抓） | 3 | ✅ 能拿到**结构化线索**（名称/时间/地点/奖池/主题），报名仍跳公众号原文 |
| 飞书报名表单（不可枚举） | 4 | ✅ `registration.url` + **`registration.qrImage`（裁好的二维码）** 直接给 |
| 腾讯文档内页 | 1 | ✅ 同上传闻线索 |
| 零散官网（一站一模板，性价比最低） | 11 | ✅ **完全不用写解析器**——这是最大的成本节省 |
| 大厂赛事页 / 活动平台 | 8 | ✅ 可与 L1 交叉验证，互为佐证 |

**一句话：第三章判定"必须人工"的那 22 场（65%），现在全部变成"自动发现 + 人工核验"。人工从「录入」降级为「确认」。**

### 6.5 接入架构（三级来源）

```
                   ┌──────────────────────────────────────┐
   L1 一手源  ────▶ │ 主办方官网 / lu.ma / 天池 / 腾讯云    │  字段即结论
   （权威）        │ lablab.ai / ETHGlobal                 │  落库 →「待审核」
                   └──────────────────────────────────────┘
                                    │
                   ┌────────────────▼──────────────────────┐
   L2 聚合源  ────▶ │   HackerTrip  /api/hackathons        │  只给线索
   （兜底）        │   全量 37 条 · 33 字段 · 含海报        │  落库 →「待核验」
                   └──────────────────────────────────────┘
                                    │
                        ┌───────────▼────────────┐
                        │  verifyAgainstSource   │  ◀── 发布前必经闸门
                        │  访问 authoritativeUrl │
                        │  比对截止/奖金/主办方    │
                        │  冲突 → 以官方为准      │
                        └───────────┬────────────┘
                                    │
                   ┌────────────────▼──────────────────────┐
   L3 人工源  ────▶ │ 公众号 / 小红书 / 飞书表单 / 腾讯文档  │  粘贴链接 → 半自动解析
   （补充）        │                                       │  落库 →「待核验」
                   └──────────────────────────────────────┘
```

**去重规则**：`website` 归一化 URL 为主键。同一赛事被 L1 与 L2 同时命中时**合并为一条**——L1 字段优先，L2 补缺（典型是补海报、补奖池文案、补 agenda）。

### 6.6 六条铁律（写进代码，不靠自觉）

1. **六项不直接采用**：报名状态、截止时间、奖金、场地、参赛资格、主办方身份，L2/L3 来的必须回溯 `authoritativeUrl` 核验后才发布。
2. **冲突以官方为准**，且必须写 `deadlineHistory` 留痕——**禁止静默改数字**。
3. **核验不了就标出来**：官网打不开 → `verifyState=pending`，前台显示灰色「待核验」，不装成已核验。
4. **绝不高频**：上游 `Cache-Control: max-age=300`，我们每日 2–4 次即可。
5. **标明身份**：带自定义 UA（如 `FutureZaowuBot/1.0 (+联系邮箱)`），并遵守其 `robots.txt` 对 `/api/` 之外路径的限制。
6. **不镜像、不转售、不声称原创**：不全量转发其数据，不对外暴露成我们的 API。

### 6.7 更优路径：直接把关系做正规（建议尽早）

| 动作 | 理由 |
|---|---|
| 发邮件 `support@hackertrip.space` | 它在 `llms.txt` 里**主动留了这个邮箱**用于「补充来源或申请更正」——谈数据合作有正规入口 |
| 它是开源项目 | `github.com/Jayden72Huang/hacker_trip`，作者对生态开放的概率高 |
